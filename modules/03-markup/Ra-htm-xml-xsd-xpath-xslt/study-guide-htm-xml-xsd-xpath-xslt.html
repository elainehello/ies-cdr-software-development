XML: the data, and the tree XPath sees

XML stores data with no formatting. Every other technology in this guide reads it as a tree of nodes, so learn to see that tree before anything else.

/ ← document node (root node) └─ contenido ← root ELEMENT (document element) └─ eventos └─ evento ← element node ├─ @id_evento = "A335" ← attribute node ├─ @opcional = "no" ├─ fecha_evento │ └─ "20.6.2011" ← text node └─ titulo └─ "Verbena popular"

Seven node types in XPath: root (document), element, attribute, text, comment, processing instruction, namespace. In exams you mostly use the first four.

The five predefined entities: &lt; < · &gt; > · &amp; & · &quot; " · &apos; '. Use <![CDATA[ … ]]> for a block of raw text that may contain < and &.

Element or attribute? Attributes hold simple metadata about an element (ids, codes, flags like opcional). Elements hold content that can repeat or have structure. An attribute can't repeat and can't have children.

Mixed content means text and elements interleaved, like <texto>… el <persona>Secretario</persona> inauguró …</texto> in the noticias. In XSD it needs mixed="true".

Is it well-formed?

Same check in the terminal: xmllint --noout fichero.xml (no output = well-formed).

XSD: the rules the XML must follow

Well-formed means the syntax is correct. Valid means it also obeys a schema: the right elements, in the right order and number, with the right types. An XSD is itself an XML document, so it must be well-formed too.

Decide each element in 3 questions

Does it have attributes OR child elements? ├─ NO → simple element: <xs:element name="titulo" type="xs:string"/> │ need limits on the value? → <xs:simpleType><xs:restriction base="…"> + facets └─ YES → <xs:complexType> ├─ children in fixed order? → <xs:sequence> ├─ only ONE of them? → <xs:choice> ├─ all, any order, max once? → <xs:all> ├─ text + attribute only? → <xs:simpleContent><xs:extension base="xs:string"> ├─ text mixed with children? → <xs:complexType mixed="true"> └─ attributes go AFTER the sequence/choice, inside complexType

XPath: pointing at nodes

An XPath expression is a chain of steps. Each step is axis::node-test[predicate], where the axis gives the direction, the node test says which names, and the predicate is the filter. The result of each step becomes the starting point (context) of the next one.

//alumno[@beca='si']/nombre step 1 //alumno from the root, any depth, elements named alumno → e01 e02 e03 e04 [@beca='si'] keep those whose beca attribute is 'si' → e03 step 2 /nombre from EACH of those, go to child nombre → <nombre>Fernando</nombre>

Absolute, relative, and the context node

Absolute paths start with / and are always evaluated from the document root, wherever you are.

Relative paths start with a name, . or .. and are evaluated from the context node: the node you're "standing on".

In XSLT the context changes: inside <xsl:template match="evento"> or <xsl:for-each select="//evento">, the context is one evento at a time, so you write titulo, not //titulo.

context = evento A335 titulo → its titulo ✔ ./titulo → same thing @id_evento → "A335" ✔ ../evento → all 3 eventos (siblings + itself) //titulo → ALL 5 titulos in the document ✘ usual bug .//titulo → titulos inside this evento only

The idea behind the hard questions: comparing node-sets

When one side of = is a set of nodes, the comparison is true if any node in the set matches. That's what makes the “join” questions (19–25 on your sheet) work: you look up values in one branch of the tree and use them to filter another branch, like a SQL JOIN … ON.

Asignaturas that Luisa studies: //asignaturas/asignatura[ @id = //alumno[nombre='Luisa']//asignatura/@codigo ]/nombre └┬┘ └──────────────── inner path ──────────────────┘ │ = { "a02", "a01" } (a SET of codes) for each asignatura: │ a01 = {a02,a01} ? ✔ true (matches a01) → Ofimática a02 = {a02,a01} ? ✔ true (matches a02) → Ingeniería del Software a03 = {a02,a01} ? ✘ false … SQL equivalent: SELECT a.nombre FROM asignatura a JOIN matricula m ON a.id = m.codigo WHERE m.alumno = 'Luisa'

How to build one: (1) write the inner path alone and check it returns the codes; (2) write the outer path without a predicate; (3) put them together: outer[@id = inner]. Test step 1 in the tester before moving on.

    XSLT: rules that turn the tree into HTML

    An XSLT stylesheet is an XML file of template rules: “when you find a node that matches this pattern, output this”. XPath picks the nodes, and literal HTML in the template is copied to the output as it is.

    The skeleton you start every answer with

    The 8 instructions in your syllabus

    InstructionDoesTypical use

    Pull vs push: for-each vs apply-templates

    Pull (for-each): one big template that goes and fetches what it wants, in the order you write it. Easy to read, and a good fit for tables.

    Push (apply-templates): you send nodes out, and each node type has its own small template. Better when the structure varies. This is the style of your teacher's eventos_choose.xslt.

    Built-in rules (they exist even if you don't write them): match "/" or any element → apply-templates to its children match text or @attribute → output its text That's why a stylesheet with NO templates prints all the text of the XML in one block.

    Exam day: four RAs in one sitting

    Every RA also has a questionnaire. These are the questions that keep coming back in this module, followed by a routine for the practical part.

    Order of attack

    1. Read the XML first and sketch its tree (2 minutes). Mark which things are attributes (@) and which are elements.
    2. XPath questions next: each one is independent and quick to check by reasoning on your sketch.
    3. XSD: work top-down with the 3-question decision. Write attributes last, after the sequence.
    4. XSLT: draw the target HTML first, then mark “once” vs “per node”, then write the skeleton and fill it in.
    5. HTML: count cells per row whenever there's a rowspan/colspan, and check every label for has a matching id.

    Theory questions to be ready for

    • Well-formed vs valid. DTD vs XSD (XSD is XML, has data types, and controls the number of occurrences).
    • Simple vs complex type. sequence vs choice vs all.
    • What XPath is used for (XSLT, XQuery, XPointer). The node types. What the context node is.
    • XSLT vs CSS: XSLT can reorder, filter, compute and group; CSS only styles.
    • for-each vs apply-templates. if vs choose.
    • GET vs POST. name vs id. th vs td.

    Last check before handing in

    • Is every XSLT tag closed? value-of, output, sort and apply-templates self-close />.
    • Single quotes inside double-quoted attributes: test="@opcional='no'".
    • < written as &lt; inside test and select.
    • Inside a for-each, paths are relative: no // unless you mean the whole document.
    • xsl:sort is the first child, with data-type="number" for numbers.
    • Attribute names in XPath carry @. Element names are copied exactly from the XML.
    • XSD: the prefix (xs:) is the same everywhere, maxOccurs="unbounded" is spelled right, and the attribute goes after the sequence.
